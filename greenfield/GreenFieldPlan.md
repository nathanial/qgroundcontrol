# Greenfield Migration Plan

## Context and Goals
- **Objective**: Incrementally reproduce QGroundControl user-facing functionality inside the Electron + Typescript + Rust scaffold without destabilising the existing Qt/C++ codebase.
- **Principles**: ship small slices, keep the Rust boundary authoritative for device/system integration, and maintain data-model compatibility with MAVLink + parameter metadata generated by the legacy project.
- **Current Baseline (September 26, 2025)**: Desktop shell with napi-rs bridge exposing synchronous status calls. No autopilot plumbing, persistence, or UI flows yet.

## Architecture Snapshot
- **Renderer (Typescript/React-ready)**: rapid iteration layer for mission UX, telemetry dashboards, configurators.
- **Preload Bridge**: typed channel for message passing (`window.backend`).
- **Rust Core**: native services: MAVLink transport, device discovery, mission file IO, video ingestion, sensor fusion extensions.
- **Legacy Reference**: QGroundControl repo remains the canonical source for protocol handling, parameter metadata, and mission business logic until reimplemented.

## Migration Phases

### Phase 0 – Foundational Hardening (Week 0-2)
- Finish napi scaffolding: async command support, structured errors, hot reload (`npm run dev:native`).
- Establish shared domain model crates (Rust) + generated TypeScript bindings.
- Introduce integration test harness (Vitest + `cargo test`) for boundary coverage.

### Phase 1 – Core Connectivity (Week 2-6)
- Port MAVLink transport using existing QGC `libs/mavlink` as reference; expose async connect/disconnect, heartbeat stream, and parameter fetch primitives.
- Implement serial/UDP device discovery service in Rust; surface device list and connection status events to renderer.
- Build mission/event logging pipeline (Rust -> TS) mirroring QGC FactGroup events.

### Phase 2 – Telemetry & Status UI (Week 4-10, overlaps Phase 1)
- Create TypeScript state manager (Zustand or Redux Toolkit) hydrated from Rust events.
- Render health dashboard: vehicle heartbeat, GPS, battery, flight mode.
- Implement parameter browser with read-only capability; validate against live autopilot using simulated data (SITL).

### Phase 3 – Mission Planning & Upload (Week 8-14)
- Port mission data structures (Rust) reusing QGC FactSystem metadata.
- Provide mission editor UI with map canvas (Leaflet/Mapbox GL) and pattern templates.
- Add mission upload/download flows via Rust using MAVLink Mission protocol; include optimistic concurrency + rollback semantics.

### Phase 4 – Configuration & Calibration (Week 12-20)
- Migrate parameter editing with staged apply + validation.
- Implement sensor calibration workflows (compass, accelerometer) by wrapping existing QGC state machines in Rust.
- Add aircraft setup wizard in renderer using reusable components.

### Phase 5 – Media & Advanced Features (Week 18-26)
- Reintroduce video streaming (GStreamer or FFmpeg pipeline in Rust with WebRTC bridge to renderer).
- Implement geofence/rally/ROI tools; export/import mission files.
- Integrate log download & analysis pipeline (Rust -> wasm analysis library where appropriate).

## Cross-Cutting Workstreams
- **QA & Tooling**: nightly canary build, Playwright smoke tests, autopilot SITL CI.
- **Documentation**: keep `docs/` synced with new API surfaces and migration status dashboard.
- **Performance**: profiling budget for renderer (Chrome DevTools) and Rust core (criterion, tracy integrations).
- **Packaging**: electron-builder targets for macOS, Windows, Linux; notarization and code signing.

## Collaboration & Rollout Strategy
- Maintain feature parity matrix comparing legacy Qt app vs greenfield; update weekly.
- Release internal alpha once Phase 2 completes; gather pilot feedback before decommissioning Qt views.
- Plan for coexistence mode: allow Qt app to launch Electron shell for specific workflows until full switchover.

## Risks & Mitigations
- **Protocol Drift**: automate MAVLink XML ingestion to regenerate models; add regression tests against QGC reference logs.
- **Performance Regression**: keep computationally heavy logic in Rust; stream data incrementally to renderer.
- **Team Familiarity**: schedule pairing sessions for TS/Rust cross-skilling; document best practices in `greenfield/docs/`.
- **Legacy Dependencies**: audit Qt-only services; replace with Rust crates or FFI shims before removing Qt modules.

## Definition of Done
- Feature parity for mission planning, telemetry, configuration, logging.
- Installers generated via CI for all target platforms with automated smoke tests.
- Legacy Qt launcher deprecated, with final release notes and migration guide for operators.
